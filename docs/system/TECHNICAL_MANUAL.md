# Technical Manual

## 1. What the system is

The UMBRAL information system is the Flask application of Activity 1 extended with a database, accounts, roles and the business processes of the game's players and accounts. The public pages (cover, six CRISP-ML phases, live demo, PDF reports) stay public. Everything under `/app` needs a signed-in user.

## 2. Code structure

| Path | Content |
| --- | --- |
| `app/app.py` | Flask app of Activity 1 (documentation pages, demo, API) + `init_system(app)` |
| `app/system/__init__.py` | Configuration from environment variables, database, sign-in, CSRF, error log, first administrator, CLI commands |
| `app/system/models.py` | Database model (SQLAlchemy): users, players, saved_games, play_sessions, records, inferences, recommendations, tickets, error_log, audit_events |
| `app/system/auth.py` | Registration, sign-in, sign-out, lockout, CSRF, `role_required`, per-player authorization |
| `app/system/views.py` | Operational modules (blueprint `/app`) |
| `app/system/ml_service.py` | The model inside the workflow: analysis of a session, decision rule, outcome tracking, drift (PSI) |
| `app/system/seed.py` | Demo data from the Activity 1 TEST players (`flask seed-demo`) |
| `app/templates/system/` | Pages of the system |
| `src/umbral_ml/` | Activity 1 pipeline: data, training, `predict.py` (features used by training AND serving) |
| `models/` | Saved models (`*.joblib`) and `model_card.json` (version) |
| `tests/test_system.py` | Automatic tests (pytest) |
| `tools/operational_review.py` | Operational review of the deployed system |
| `tools/gen_system_figures.py` | Architecture and database diagrams |

## 3. Install and run locally

1. Install Python 3.14.
2. `python -m venv .venv` and activate it (`.venv\Scripts\activate` on Windows).
3. `pip install -r requirements.txt`
4. Without `DATABASE_URL` the app uses a local SQLite file (`instance/umbral_system.db`).
5. Create the first administrator with environment variables `ADMIN_USERNAME` and `ADMIN_PASSWORD` (created on start-up if there is no administrator), or with `flask --app app.app create-user <name> admin`.
6. Optional demo data: `flask --app app.app seed-demo`.
7. Run: `flask --app app.app run` and open `http://127.0.0.1:5000`.
8. Tests: `pip install pytest` and `python -m pytest -q tests`.

## 4. Configuration (environment variables)

| Variable | Meaning |
| --- | --- |
| `DATABASE_URL` | PostgreSQL connection string (Supabase). `postgres://` and `postgresql://` are accepted. Without it: SQLite (development only). |
| `SECRET_KEY` | Signs the session cookie. Required when `RENDER` or `PRODUCTION` is set. |
| `ADMIN_USERNAME`, `ADMIN_PASSWORD` | First administrator, created only if there is no administrator. |
| `RENDER` | Set by Render. Turns on secure cookies and makes `SECRET_KEY` mandatory. |

`.env.example` shows the format. Real values are never written in the repository.

## 5. Database setup (Supabase PostgreSQL)

1. In Supabase open the project of the game → **Connect** → **Session pooler** and copy the URI (port 5432). It has the database password.
2. Put it in Render as `DATABASE_URL` (Environment, secret).
3. On the first start the app creates all the tables (`db.create_all()`); there is no manual SQL step. The tables are separate from the game's own tables (`umbral_users`, `umbral_saves`...), so nothing of the game changes.
4. To start again from zero, drop the ten tables of section 2 in Supabase (Table editor) and restart the service.

## 6. Deployment on Render

1. Render → **New → Blueprint** → this repository (`render.yaml`). The service runs `gunicorn app.app:app`.
2. In **Environment** set `DATABASE_URL`, `ADMIN_USERNAME` and `ADMIN_PASSWORD`. `SECRET_KEY` is generated by Render.
3. Deploy. Check `https://<service>.onrender.com/api/health`: `status` and `database` must say `ok`.
4. Sign in as the administrator, create the analyst and player test accounts (Users page after they register, or `create-user` in the Render Shell).
5. Run the operational review (section 10) against the public URL.
6. Every push to `master` redeploys the service.

## 7. Security

- Passwords: Werkzeug `generate_password_hash` (scrypt with a random salt). The plain password is never stored or logged.
- Public registration always creates a **player**. The form has no role field, and a role sent by hand is ignored (tested).
- Roles are changed only by an administrator. Nobody can change their own role, and the last active administrator cannot be removed.
- 5 wrong passwords lock the account for 5 minutes. The error message does not say which part was wrong.
- Every form has a CSRF token checked on the server. Cookies: HttpOnly, SameSite=Lax, Secure in production. The session id changes after sign-in.
- Authorization is checked on the server for every route (`role_required`) and for every object (`player_or_403`: a player only reaches their own profile, saves, sessions, records and tickets). Forbidden attempts are written to `audit_events`.
- Headers: `X-Content-Type-Options`, `X-Frame-Options: DENY`, `Referrer-Policy`, `Cache-Control: no-store` on private pages.
- The JSON API (`/api/predict/*`) needs a signed-in session and answers `401` without it.

## 9. The model in the workflow

- Models: the ones chosen in Activity 1 (`models/next_action.joblib`, `models/hit.joblib`). They are not retrained by this application.
- Features: built by `src/umbral_ml/predict.py` (`action_row`, `hit_row`), the same functions used to evaluate the models. Preprocessing (imputation, one-hot encoding, scaling) is inside each saved pipeline. The player's earlier sessions are given as history (as in training, capped at 1,000 actions).
- Inference runs on the server (`ml_service.analyze_session`) and through the API.
- Every inference is stored in `inferences`: date, user, player, session, model name, model version (`source + training date` from `model_card.json`), input, result, latency, and the number of predictions compared with the real next action.
- Decision rule (`ml_service.DECISION_RULE`): lower one level when the player lost or died 3+ times per 10 minutes AND the hit risk is 36%+ (the top quarter of the model's predictions on the Activity 1 test players), or 5+ deaths per 10 minutes; raise one level when the player won with at most 1.5 deaths per 10 minutes and a risk of 22% or less; otherwise keep. Only one pending recommendation per player.
- An approved recommendation changes the player's difficulty. The next analyzed session of the player is compared with the session before the change (`effective`).

## 10. Monitoring and maintenance

- **Errors:** every unexpected error is printed to the Render log and stored in `error_log` (path, type, message, traceback). Monitoring page → Last errors.
- **Inference requests and response times:** table `inferences` (latency in ms). Monitoring page: count, mean, p95.
- **Predictions vs. real outcomes:** in each analyzed session every prediction of the next action is compared with the real next action, so accuracy is known at once. Monitoring shows it per week; alarm when a week is 5 points below the first three weeks. Difficulty changes are checked with the next session.
- **Changes in the input data:** PSI between the action mix of the training data and the sessions of the last 30 days (warning 0.1, alarm 0.2), the same rule as Phase 6 of Activity 1.
- **Versioning:** the version of a model is its data source + training date in `models/model_card.json`. Models and model card are versioned in Git; every inference keeps the version used.
- **Updates and retraining:** the GitHub Actions job `weekly-retrain` (Mondays) downloads the real anonymous play log, retrains, evaluates with the fixed rule of Activity 1 and commits new models only if they pass. Render redeploys and the new version appears in Monitoring → Model versions. Retrain also when the PSI is above 0.2, the weekly accuracy falls 5 points, a game update changes the fights, or the real data doubles. To go back to an old version: `git revert` of the "Weekly retrain" commit.
- **Health:** `/api/health` (status, database, model version) for Render's health check.
- **Operational review:** `python tools/operational_review.py <url>` with the `REVIEW_*` variables (see the script). It writes `reports/operational_review.json`.
- **Weekly routine:** J.A reviews Monitoring (accuracy, PSI, errors) and the rejected recommendations; J.Q reviews tickets and opinions; J.P checks the game after each release.

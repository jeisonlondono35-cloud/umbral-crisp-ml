5.2 Demo

Open the live demo → Enter a player's recent actions and the situation; it returns the predicted next action with its probabilities (and what the current in-game model would say), and the probability that a chosen boss attack hits.

5.3 API: inputs, outputs

POST /api/predict/next

{
  "history": ["shoot", "shoot", "dodge", "shoot"],   // last actions, oldest first: {{ ACTIONS|join(' | ') }}
  "w": 2, "mode": "story", "diff": 1,                 // world 1-5, story | ole | pan, difficulty 0-3
  "hp": 4, "ne": 160, "boss": true,                   // life, distance to enemy (px), boss fight
  "is_start": false                                   // true = more than 4 s since the last action
}
→ {"prediction": "shoot", "probability": 0.52, "proba": {"shoot": 0.52, ...},
   "in_game": {"prediction": "dodge", "probability": 0.51}, "model": "...", "latency_ms": 3.1}

POST /api/predict/hit

{"move": "feint", "close": 1, "far": 0, "in_air": 0, "blocking": 1, "moving": 0, "low_hp": 0,
 "expects_evade": 0.0, "w": 2, "diff": 1, "mode": "story"}
→ {"p_hit": 0.64, "known_move": true, "model": "...", "latency_ms": 2.0}

POST /api/predict/dodge · GET /api/health · GET /monitoring/live

{"history": [[20, 5], [30, -10]]}  → {"ox": 26.4, "oy": -2.4}      // previous dodge offsets (px, boss frame)
GET /api/health   → status, data source, training date, chosen models
GET /monitoring/live → last logged requests, mean latency, feedback received

Try it: curl -X POST {{ request.host_url }}api/predict/next -H "Content-Type: application/json" -d '{"history":["shoot","dodge"],"boss":true}'

5.4 Dependencies and how to run it

python -m venv .venv && .venv\Scripts\activate          # (Linux/macOS: source .venv/bin/activate)
pip install -r requirements.txt                         # Flask, scikit-learn, pandas, numpy, matplotlib, joblib, reportlab, requests, gunicorn
python pipeline.py                                      # download data, simulate, prepare, train, evaluate, monitor, PDF
python -m flask --app app.app run                       # http://127.0.0.1:5000
gunicorn app.app:app                                    # production (Render: see render.yaml)

5.5 First-use instructions

  1. Open the cover page and read the six phases in order (top menu).
  2. Go to Demo, write the recent actions separated by commas (e.g. shoot, shoot, dodge), set the situation and press Predict.
  3. Read the predicted action and its probability bar; compare with "in-game model".
  4. For a boss attack, choose the attack and tick the situation; read the hit probability.
  5. Use the form at the bottom of this page to send an opinion or report an incident.

5.6 Integration plan with the information system of Activity 2 (game + web + Supabase)

StepWhatWhoStatus
1 · Data inThe game (Godot: web, Android, PC) writes anonymous gameplay batches to Supabase with the public key (umbral_ml_log_put), next to the existing accounts, saves, records and ML accuracy tables.J.P / J.Adone
2 · Trainingpipeline.py reads them with umbral_ml_log_export, retrains, writes the model and the report; a weekly GitHub Action runs it and Render redeploys this app.J.Adone
3 · ServingThis app on Render exposes /api/predict/*; the website of the game (Render) links to it.J.Qdone
4 · In the gameBosses keep the in-game model as the always-available fallback (it works offline). When online, at the start of a boss fight and every 2 s, the boss asks /api/predict/next (HTTPRequest, like cloud.gd) and uses the answer only if it is fresher than 2 s. If on real data the winner is linear or Markov, its parameters are exported to a JSON shipped with the game and the network is not needed.J.Pplanned
5 · Feedback loopAccuracy per account keeps flowing to umbral_ml_public; the in-game "Report error" form and this app's form collect opinions; Phase 6 indicators are reviewed weekly.J.Q / J.Arunning

5.7 Monitoring, incident reports and user opinions

  • Every prediction is logged (time, model, inputs, output, latency) to monitoring/live_predictions.jsonl; summary at /monitoring/live.
  • Incidents (wrong answers, errors, slowness): the form below (type "incident"), the game's Pause → Report error, or a GitHub issue. Severity: high = API down or wrong outputs for everyone → J.A fixes or rolls back to the previous model the same day; medium = a segment worse than expected → review at the weekly meeting; low = text or UI → next release.
  • Rollback: every model is versioned in git with its model card; redeploying the previous commit restores it.
  • User opinions: the form below (rating 1–5) and the game's report form (rating 1–10); reviewed weekly with the indicators.

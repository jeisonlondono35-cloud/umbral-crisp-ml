6.2 Detecting data drift and performance loss

  • Data drift: Population Stability Index, PSI = Σ (cur − ref) · ln(cur / ref), over the categories (action, mode, difficulty) or the 10 training deciles (enemy distance). Below 0.10 stable, 0.10–0.20 watch, above 0.20 significant change.
  • Performance: every week the chosen model and the in-game model are scored on the new real actions (the log already contains the true next action). A 2-week mean is used because one week of a few players is noisy.
  • Concept drift shows as performance loss without input drift (players react differently to the same situation).

Retrain when: (1) any PSI > {{ th.psi_alert }}; (2) 2-week accuracy below the baseline − {{ (th.acc_drop*100)|int }} points; (3) a game update changes combat (new actions, bosses or attacks); (4) the real data doubles since the last training. Deploy the new model only if it passes the same Phase 4 rule on new validation players and is not worse on test than the current one; otherwise keep the current one and investigate.

6.4 Risks and quality controls

  • Bad batches are rejected by the server (size, format, rate limit of 8,000 events per player per hour) and cleaned by Phase 2 rules.
  • Unit-like checks run in the pipeline: no player in two partitions, preprocessing fitted only on train, metrics recomputed from files.
  • The in-game model stays as fallback: if the API or the new model fails, bosses keep working.
  • Fairness: accuracy and hit rate per difficulty are part of the weekly review (expert risk: "too hard", "unfair").
  • Privacy: anonymous ids only; players can switch logging off; the export only returns events.
  • Updates: model, data report and model card are committed together, so every deployed model can be traced and rolled back.

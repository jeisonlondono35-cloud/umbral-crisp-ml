Phase 2

Data Engineering

From the raw export (one JSON batch per upload) to three clean tables, with every transformation documented, evidence before and after, and a split that keeps each player in a single partition. Code: src/umbral_ml/prepare.py.

2.1 Selected sources and variables (and why)

  • Gameplay log (real when available, simulated now — same format): it is the only source with the sequence of actions, needed for a sequential target.
  • Kept: action, time gap, distance to enemy, world, mode, difficulty, life, boss scene, attack id and its 8 situation features, hit outcome, dodge offset.
  • Not used as features: p/pp (what the in-game model predicted) — kept only to measure the deployed model; ver, ids and timestamps — used for ordering and grouping, never as inputs.
  • Aggregate accuracy per account (REAL): not row-level, used as production evidence in Phases 1, 4 and 6.

Engineered features (domain knowledge)

  • prev1, prev2: the last two actions, reset to "start" after 4 s (the same "phrase" rule as the game).
  • hist_*: how often THIS player did each action before now (Laplace-smoothed) and log_hist — personalises a global model.
  • mk_*: the probabilities of the player's own online Markov chain at that moment (stacking: the global model can learn when to trust it).
  • boss: the action happens in a boss arena. family: attack family (guardian / wolf / mirror).
  • attack × situation products for the pooled logistic regression (one slope per attack, like the in-game bandit; attack list fixed from the game code).

Every sequential feature uses only earlier events of the same player.
